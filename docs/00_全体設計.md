## 1. 設計判断の記録（3案の差分と採用）

2026年8月時点で、次の3つの設計案が存在した。

- **A: 本リポジトリ初版** … 静的HTML+JSON+Decap CMS+Netlify。水色ベースで実装済み
- **B: 詳細版設計書パッケージ** … Astro+microCMS+Cloudflare Pages。コートグリーン基調。運用設計が厚い
- **C: 簡易版AI設計書** … Astro/Next.js+microCMS+Netlify Forms。白黒ベース+ネイビー/グリーン。GSAP

| 論点 | A（初版） | B（詳細版） | C（簡易版） | **採用** |
|---|---|---|---|---|
| フレームワーク | 静的HTML+JSON | Astro+TS | Astro/Next.js | **当面 A を継続**。ビルド不要＝更新反映が速く壊れにくい。ページ数・データ量が増えたら Astro 化（§6） |
| CMS | Decap CMS（Git保存・無料） | microCMS（Hobby無料） | microCMS | **Decap 継続**。追加費用ゼロ・データは常にGitに残る。スマホ操作性に不満が出た時点で microCMS へ移行（§6） |
| ホスティング | Netlify | Cloudflare Pages | Netlify | **Netlify 継続**（Identity+Git Gateway を Decap が利用中）。転送量が無料枠を圧迫したら Cloudflare Pages へ |
| フォーム | Googleフォーム（暫定） | GAS+Turnstile | Netlify Forms | **Googleフォーム→GAS**（Phase 2）。Netlify Forms は月100件で有料化するため大会エントリーに不向き。GAS はスプレッドシート集計という協会の運用資産に直結 |
| 大会ステータス | 手動切替（4状態） | **日時から自動算出（7状態）** | 記載なし | **B の自動算出を採用**。締切の過ぎた「受付中」が残る事故を設計で消す。クライアントJSで閲覧時刻判定するため、静的サイトのままでもビルド時刻固定問題が起きない |
| ナビゲーション | 8項目 | 5項目に集約 | 5項目 | **5項目に集約**（大会／協会登録／教室・イベント／協会について／お問い合わせ）。11項目ナビはスマホで機能しない |
| 配色 | 水色+グラデーション | コートグリーン | 白黒+ネイビー | **水色ベースで再設計**（発注者指定）。ブルーコート×鳥取の空・水の視覚言語に統一し、グラデーションは廃止してフラットに（design.md §3） |
| 書体 | Zen Kaku+Outfit | Zen Kaku+BIZ UDP+Barlow Condensed | Noto Sans/Inter | **B の3書体構成を採用**。本文に UDフォント（会員年齢層20〜70代への実務判断）、数字に専用書体（このサイトの主役は日付と締切） |
| アニメーション | フェードアップ多用 | 3箇所限定+シグネチャ | GSAP多用 | **B の制約を採用**（シグネチャのブラケット線描画／カードホバー／見出しフェードのみ）。GSAP は入れない（依存を増やさない） |
| シグネチャ要素 | ボール・コートラインSVG | ドロー表のブラケット線 | なし | **ブラケット線を採用**。競技団体にしか使えない形。水色パレットで再解釈 |
| 大会情報の構造 | 一覧のみ | 詳細1ページ集約（要項/ドロー/結果/ライブ） | 要項PDF DL | **B を採用**。1大会=1ページに要項・ドロー・結果を集約。結果はスクショでなく表データ |
| 緊急告知バー | なし | あり | なし | **採用**。「本日の大会は雨天中止」を1分で全ページ最上部に出せることが最重要機能のひとつ |
| モバイル固定CTA | なし | あり | なし | **採用**。受付中の大会があるときだけ画面下部に表示 |
| 画像 | 原本をGitにコミット | ビルド時に AVIF/WebP 化 | microCMS CDN 配信 | **当面 A**（原本コミット+`loading="lazy"`+寸法指定）。Astro 化と同時に B の最適化パイプラインへ。microCMS 直配信は転送量20GB/月で停止するため恒久採用しない |
| ドロー自動生成 | なし | エクスポート言及 | GAS/VBA提案 | **Phase 3 に採録**。エントリーデータ（スプレッドシート）→ドロー生成の自動化 |

**要約**: 器（ホスティング・CMS）は動いている A を維持し、中身（情報設計・状態管理・デザイン言語・運用設計）を B に置き換える。C からは「エントリーデータ→ドロー自動生成」の着想のみ採る。

## 2. リニューアルの目的（優先順）

1. **申し込みまでの導線を最短にする** … トップで「いま何に申し込めるか」が3秒で分かる
2. **更新をスマホだけで完結させる** … 会場からでも結果が出せる
3. **画像品質を端末非依存で一定にする** … 誰がどこから上げても同じ画質
4. **協会登録・大会エントリーのWEB化を受け止める土台をつくる**
5. **鳥取市テニス協会にしかない見た目にする**

## 3. 全体アーキテクチャ

```
┌────────────────────────────────────────────────┐
│ 更新者（役員・広報局）… スマホ / PC ブラウザ      │
│   └ /admin/（Decap CMS 管理画面）               │
└──────────────┬─────────────────────────────────┘
               │ Git commit（Git Gateway 経由）
               ▼
┌────────────────────────────────────────────────┐
│ GitHub  tcta-tottori/TCTA-HP                    │
│   HTML / CSS / JS / data/*.json / 画像原本      │
└──────────────┬─────────────────────────────────┘
               │ push をトリガーに自動デプロイ
               ▼
┌────────────────────────────────────────────────┐
│ Netlify（本番配信・ビルド工程なし）              │
└──────────────┬─────────────────────────────────┘
               │
   ┌───────────┴────────────┬────────────────┐
   ▼                        ▼                ▼
Googleフォーム→GAS      Googleカレンダー   LINE公式
（エントリー/登録受付→   （大会日程）       （告知配信）
 スプレッドシート集計）
```

- 公開されるのは静的ファイルのみ。サーバ保守・プラグイン更新・改ざんリスクなし
- お知らせ・大会・結果は `data/*.json`。**HTMLを触らずに更新が完結**する
- 大会の状態（受付中・締切間近など）は JSON の日時フィールドから **閲覧時に自動算出**（§4）

## 4. 大会ステータスの自動算出（本設計の要）

CMS に「状態」の入力欄を置かない。以下の日時フィールドのみ入力させる。

| フィールド | 意味 |
|---|---|
| `entryOpenAt` | エントリー受付開始日時 |
| `entryCloseAt` | エントリー締切日時 |
| `startDate` / `endDate` | 開催日（初日・最終日） |
| `drawPublished` | ドロー公開フラグ（ドロー本文の有無で代用可） |
| `resultPublished` | 結果公開フラグ（結果本文の有無で代用可） |

判定順（`js/status.js`・上から評価）:

1. 結果あり かつ `endDate` 経過 → `finished`（結果）
2. 現在時刻が `startDate`〜`endDate` → `live`（開催中）
3. ドローあり かつ 締切後 → `draw`（ドロー公開）
4. 現在時刻 > `entryCloseAt` → `closed`（受付終了）
5. 締切まで3日以内 → `closing`（締切間近）
6. `entryOpenAt`〜`entryCloseAt` の間 → `open`（受付中）
7. それ以外 → `announced`（開催予定）

これが「締切を過ぎた告知が残る」「受付中バッジの付け外しを人がやる」という現行課題への設計上の回答であり、運用負荷の削減幅が最も大きい箇所。

## 5. WEB化のフェーズ計画

| フェーズ | 内容 | 状態 |
|---|---|---|
| **Phase 1** | サイト刷新（本設計）。エントリーは既存Googleフォーム等へのリンク | ここまでを先に完成 |
| **Phase 2** | GAS 受付への統合。大会IDで分岐する単一GAS＋スプレッドシート集計。受付番号発行・自動返信メール | Phase 1 公開後 |
| **Phase 3** | 協会登録のWEB化（個人・クラブ、年度更新は前年データ引き継ぎ）。エントリーデータからのドロー自動生成（GAS） | 年度切替（4月）に合わせて投入 |
| **Phase 4** | 会員マイページ・ライブスコア統合 | 将来 |

Phase 2 以降の実装原則:
- 締切・定員チェックは**サーバ側（GAS）でも必ず**行う。クライアント表示は参考にすぎない
- 申込完了画面に**受付番号と支払期限**を表示し、同内容をメール送信（問い合わせを減らす最大の施策）
- 個人情報はサイト（リポジトリ）に一切保持しない。スプレッドシート側の共有範囲を役員限定にする
- プライバシーポリシーページを Phase 3 着手前に必ず新設する

## 7. 移行・公開計画（Jimdo → 新サイト）

1. 現行サイト全ページをPDF保存（移行漏れ防止）
2. **ドメイン `tottori-tenis.net` の管理元を最優先で確認**。Jimdo管理なら移管申請を先に完了させる（解約でドメイン喪失＝全リンク・メール死亡の最大リスク）
3. 旧URL（日本語パス）→新URLの301リダイレクト表を作成し `_redirects` に全件投入
4. プレビューURLで役員レビュー → 役員向け更新練習会（スマホ実機）
5. DNS切替 → Search Console にサイトマップ送信
6. **Jimdo解約は切替後2週間の安定稼働を確認してから**
